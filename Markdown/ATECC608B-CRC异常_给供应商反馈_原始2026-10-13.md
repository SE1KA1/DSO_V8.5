## 一、结论摘要

我们采购的 **ATECC608B-SSHDA-T** 在标准 I²C 流程下，**对所有命令都返回状态 `0xFF`（数据手册定义：CRC 或其它通信错误，命令未被正确接收、未尝试解析与执行）**。

经定位：**该器件对报文 CRC 的校验采用"16 位整体比特反转"的约定**，与数据手册规定的 CRC
（poly 0x8005 反射、init 0、低字节先发）不一致。**除 CRC 外，该器件其余行为均符合规格**（见第四节）。

我们用**对照实验**证明这不是偶然、也不是端序误解：**取 5 条格式与参数各不相同的合法命令，
每条只改动最后两个 CRC 字节，发三个变体**，结果完全一致：

| 变体 | 结果 |
|---|---|
| 官方算法 CRC（低字节先发） | **0 / 5 被接受**（全部回 `04 FF`）|
| CRC 的 **16 位整体反转** | **5 / 5 被接受** |
| CRC 的两个字节**交换**（高字节先发） | **0 / 5 被接受**（全部回 `04 FF`）|

**此外还有第二项、与 CRC 无关的独立硬缺陷**：该器件的**随机数发生器返回固定图案** ——
连续两次 `Random` 读到**完全相同**的 32 字节，且内容本身是 `FF FF 00 00` 的重复图案（见 3.8 节）。
对一颗密码芯片而言，随机源是**核心安全功能**，这是比 CRC 更难辩解的功能性失效。

**请求**：请用**同批次**器件复测（第七节给出 5 分钟即可完成的复现步骤）；若同批同样表现，
请确认批次并安排换货；若仅此一件异常，请按**不良品**换货。

## 三、关键证据

### 3.1 实验设计（对照矩阵）

命令帧格式：`[word=0x03][Count][Opcode][Param1][Param2L][Param2H][Data…][CRC_L][CRC_H]`，
CRC 覆盖 `Count…Data`。每条命令发三个变体，**除最后两个 CRC 字节外，其余字节逐字节完全一致**。
判据只看**状态字节**：`04 FF` = 该帧**被拒**；其它（`04 00`/`04 03`/`07 …`/`23 …`）= 该帧**被接受**。
（数据手册明确 `0xFF` 是"未尝试解析或执行"，即芯片**先验 CRC、再解析**，故此判据与命令本身是否成功无关。）

选取的 5 条命令均为**只读或只写易失寄存器**、且 opcode / 参数 / **帧长**各不相同：

| # | 命令 | Opcode | 参数 | 帧长 | CRC 覆盖面 |
|---|---|---|---|---|---|
| 1 | Info (Revision) | `0x30` | P1=00 | 8 B | 5 B |
| 2 | Random | `0x1B` | P1=00 | 8 B | 5 B |
| 3 | Read 32 字节（Config） | `0x02` | P1=**80** | 8 B | 5 B |
| 4 | Read 4 字节（Config） | `0x02` | P1=**00** | 8 B | 5 B |
| 5 | Nonce（pass-through） | `0x16` | P1=03 + **32 B 数据** | **40 B** | **37 B** |

（`resp` 为该命令应答的前 4 个字节；`tail` 为发送帧的最后两个 CRC 字节。）

### 3.3 被接受的帧确实被**正确执行**（不是统一回退应答）

这一点很重要：`rev16` 变体被接受后，芯片返回的是**语义正确的应答**：

| # | 应答 | 说明 |
|---|---|---|
| 1 | `07 00 00 60 …` | Count=7 + RevNum `00 00 60 03` —— 真实的器件版本号 |
| 2 | `23 FF FF 00 …` | Count=`0x23`=35 ⇒ **32 字节随机数** —— Random 真的执行了 |
| 3 | `23 01 23 29 …` | Count=`0x23` + 配置区前 4 字节 `01 23 29 16` —— 配置区真的读出来了 |
| 4 | `07 01 23 29` | 4 字节读回**同一段** —— 与 #3 交叉一致 |
| 5 | `04 00 03 40` | **状态 `0x00` = 成功** —— Nonce 真的执行成功 |

### 3.4 三条独立的"帧-CRC 自洽"验证

除上述命令外，该器件**自己发出的**状态帧，其 CRC 也只有在 16 位反转后才自洽：

| 帧内容 | 标准 CRC-16/ARC | `rev16` | 器件实际发出的尾字节 |
|---|---|---|---|
| `04 11`（唤醒后未收命令）| `0xCCC2` | `0x4333` | **`33 43`** ✔ |
| `04 FF`（CRC 错）| `0x8042` | `0x4201` | **`01 42`** ✔ |
| `04 00`（Nonce 成功）| `0xC002` | `0x4003` | **`03 40`** ✔ |

### 3.5 我们的 CRC 实现符合标准（可自行验算）

```python
def crc16_arc(data):      # 数据手册规定：poly 0x8005 反射(0xA001)、init 0、低字节先发
    crc = 0
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc & 0xFFFF

def rev16(v):             # 16 位整体反转
    r = 0
    for i in range(16):
        r = (r << 1) | ((v >> i) & 1)
    return r & 0xFFFF

assert crc16_arc(b"123456789") == 0xBB3D                            # 公开标准向量

# 第三节 3.2 里 5 条命令的标准 CRC（覆盖 Count..Data）—— 与日志逐项吻合
assert crc16_arc(bytes([0x07,0x30,0x00,0x00,0x00])) == 0xC0BA       # #1 Info
assert crc16_arc(bytes([0x07,0x1B,0x00,0x00,0x00])) == 0x24B3       # #2 Random
assert crc16_arc(bytes([0x07,0x02,0x80,0x00,0x00])) == 0x90B5       # #3 Read 32B
assert crc16_arc(bytes([0x07,0x02,0x00,0x00,0x00])) == 0x78B4       # #4 Read 4B
# #5 Nonce：Count=0x27，CRC 覆盖 37 字节
assert crc16_arc(bytes([0x27,0x16,0x03,0x00,0x00] + list(range(0xA5, 0xA5+32)))) == 0xC0B0

# 器件**接受**的正是它们的 16 位反转（日志中 tail 一列）：
assert rev16(0xC0BA) == 0x5D03       # -> tail 03 5D  （被接受）
assert rev16(0x24B3) == 0xCD24       # -> tail 24 CD  （被接受）
assert rev16(0x90B5) == 0xAD09       # -> tail 09 AD  （被接受）
assert rev16(0x78B4) == 0x2D1E       # -> tail 1E 2D  （被接受）
assert rev16(0xC0B0) == 0x0D03       # -> tail 03 0D  （被接受）

# 器件**自己发出**的应答帧 CRC 也只在反转后自洽（3.4 节）：
assert rev16(crc16_arc(bytes([0x04,0x11]))) == 0x4333   # 实测尾字节 33 43
assert rev16(crc16_arc(bytes([0x04,0xFF]))) == 0x4201   # 实测尾字节 01 42
assert rev16(crc16_arc(bytes([0x04,0x00]))) == 0x4003   # 实测尾字节 03 40（Nonce 成功应答）
```

**以上每条断言我们已用一份独立脚本（与固件无关的实现）复算，与器件实测日志逐项吻合。**

另外，逻辑分析仪在**器件引脚处**解出的线上字节与我们发出的帧逐字节一致（`03 07 30 00 00 00 BA C0`），
排除主机侧位序/时序问题。

### 3.6 为什么不能解释为"端序约定不同"

- 若只是**字节序**问题，则 `swap` 变体（高字节先发）应当被接受 —— 实测 **5/5 被拒**。
- 若只是**位序**问题，则"仅按位反转、保持字节序"应当被接受 —— 实测同样**被拒**。
- **只有"两者同时"（即 16 位整体反转）才被接受**。
- 更根本地：该器件对**非 CRC 字节**的解析是标准行为（它正确执行了 5 条不同命令、回了结构正确的应答），
  且它自己发出的帧里非 CRC 字节也不镜像（`04` 的位反转是 `20`，实测就是 `04`）。
  ⇒ **线上传输的位序是标准的，差异只存在于它的 CRC 计算/校验算法内部。**

### 3.7 为什么不是"型号差异"

CRC 参数是 ATECC/ATSHA 系列**统一的协议规定**；Microchip 官方库 CryptoAuthLib 对
ATECC608A / 608B 及各 Trust 预置型使用**同一份** CRC 例程，**没有按型号分支**。
ATECC608A/B 的差异在功能集与出厂预置内容，不在 I²C 帧 CRC。
⇒ 该现象**不能**用型号差异解释。

### 3.8 追加：随机数发生器返回固定图案（与 CRC 无关的**独立**功能缺陷）

对 `Random`（`0x1B`，无种子；命令帧 `03 07 1B 00 00 00 24 CD`）连读两次，各读满 32 字节数据：

```
read #1 : payload 前 8 字节 = FF FF 00 00 FF FF 00 00
read #2 : payload 前 8 字节 = FF FF 00 00 FF FF 00 00
=> 两次 32 字节**完全相同**，且内容本身是固定重复图案
```

两次 32 字节全同的偶然概率 ≈2⁻²⁵⁶；而且这不是"输出缓冲区未刷新"（那也会随命令更新），
而是**固定值**。真品 ATECC608B 的 TRNG 是数据手册承诺、并经认证的核心安全功能，**每次返回新值**。

⇒ 请确认真品不会出现该现象。若确认，则本器件**不具备可用的随机源** —— 这是与 CRC 问题
**相互独立**的第二项硬性功能缺陷，且**无法用"端序/实现细节差异"解释**。
