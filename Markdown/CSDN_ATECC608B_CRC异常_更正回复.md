# 【更正】ATECC608B CRC“异常”与“TRNG 是桩”——两个结论都错了，原因如下

> 这是对求助帖的**结案更正**。原帖中“CRC 只接受 16 位反转”“随机源返回固定图案（疑似仿制/缺陷）”
> 两个判断**均已撤回**。感谢帖下各位的回复，尤其感谢指出“位序/反射”方向的网友——方向完全正确。

---

## 一、先给结论

| 原帖说法 | 实际情况 |
|---|---|
| ❌ 器件 CRC 不标准，只接受 16 位整体反转 | ✅ **我们的 CRC 变体算错了**。器件与 Microchip 官方 `atCRC()` 完全一致 |
| ❌ TRNG 返回固定图案 ⇒ 桩实现/仿制件 | ✅ **`FF FF 00 00 …` 是配置区未锁定时的出厂测试图案**，数据手册规定行为 |
| ❌ 数据区不可用、GenKey 恒失败 ⇒ 装不进密钥 | ✅ 出厂 `SlotConfig` 策略 + 未锁定状态所致，**不是缺陷** |

一句话：**这颗 ATECC608B 一切正常，只是还没被配置和锁定。**

---

## 二、CRC：网友的方向对，但给的代码不是答案

帖下回复指出的关键点是 **“ATECC 的 CRC 是位反射（LSB-first）的”**——这是对的。
但回复里给出的实现：

```c
crc = (crc >> 1) ^ 0xA001;   // 反射多项式 0xA001
```

**与我们当时已经用的实现逐字节等值**（我拿它的代码和我们的代码对同一批帧算了一遍，
结果全部相同）。所以照抄那段代码**不会改变任何结果**——因为那正是被器件拒绝的值。

真正被器件（也是被官方 `atCRC()`）接受的是：

```c
/* poly 0x8005、init 0、输入字节按 LSB-first 处理（不反射寄存器，只反射输入位序） */
static uint16_t atecc_crc16(const uint8_t *d, uint16_t len)
{
    uint16_t crc = 0u;
    uint16_t i; uint8_t j, b;
    for (i = 0u; i < len; i++) {
        b = d[i];
        for (j = 0u; j < 8u; j++) {
            if ((((crc >> 15) & 1u) ^ (uint16_t)(b & 1u)) != 0u)
                crc = (uint16_t)((crc << 1) ^ 0x8005u);
            else
                crc = (uint16_t)(crc << 1);
            b >>= 1;                 /* 关键：输入位 LSB 先处理 */
        }
    }
    return crc;
}
```

**自检向量**（用 Microchip 官方库导出的 `atCRC()` 实测得到，可自己核对）：

| 输入 | CRC | 线上字节（低字节先） |
|---|---|---|
| `"123456789"` | `0xBCDD` | — |
| `04 11` | `0x4333` | `33 43` |
| `04 FF` | `0x4201` | `01 42` |
| `07 30 00 00 00`（Info） | `0x5D03` | `03 5D` |
| `07 1B 00 00 00`（Random） | `0xCD24` | `24 CD` |

换成上面的实现后：**5 条不同命令的标准 CRC 全部被接受（5/5）**，三个故意写错的变体
（16 位反转 / 字节交换 / 含 word 地址覆盖）全部 0/5。

> ⚠️ 顺带更正一条常见误解：帖子回复里提到“CRC 覆盖含 word address”——我们专门加了第 4 个
> 变体在硬件上验证，**0/5 被接受**，所以 `0x03` 不进 CRC。（两段传输各自带 CRC 这点是对的。）

## 三、TRNG：固定图案是“未锁定”的出厂测试输出

我们原帖把 `Random` 连读两次得到完全相同的 `FF FF 00 00 …` 当成“桩实现/仿制”的证据——
**这是错的**。ATECC608A/B 在 **配置区（Config Zone）锁定之前**，RNG 会固定返回这个图案，
用于产线/联调验证数据通路；**锁定后才输出真随机数**。

这一行为在下列来源中都有记载（原帖作者也是后来才补上这个前置条件）：

- Microchip 数据手册（锁定前 RNG 固定返回 `FF FF 00 00 …`）；
- GitHub `cryptoauthlib` Issue #121（用户实测同一图案，示波器确认是芯片实际输出）；
- SODAQ 官方教程（未配置前命令要么报错、要么返回测试输出）；
- Hardwear.io 关于 ATECC508A 的演讲（“prior to the Configuration zone being locked, the RNG
  produces 0xFF,0xFF,0x00,0x00…”）。

**判据也要跟着改**：看到固定图案时，先读配置区 `0x56`（LockValue）与 `0x57`（LockConfig）——
两者为 `0x55` 就是未锁定，图案属预期；只有**已锁定还返回固定图案**才是真异常。

```c
/* 读配置区 block2 (0x40-0x5F) 后 */
unlocked = (cfg2[0x56] == 0x55 && cfg2[0x57] == 0x55);
```

我们这颗实测：`lockval@56=55 lockcfg@57=55 slotlock@58=FFFF` ⇒ 未锁定 ⇒ 图案完全正常。

## 四、数据区 / GenKey 的 `0x0F` 同理

出厂默认 `SlotConfig` 本身就是“拒绝访问”的配置，例如：

| 槽 | SlotConfig | 含义 |
|---|---|---|
| 0 | `0x2083` | WriteConfig=2、IsSecret=1、ReadKey=3 ⇒ 不可写、不可读 |
| 5 | `0x8F8F` | WriteConfig=8(Never)、ReadKey=15(Never) ⇒ 完全不可读写 |
| 8–14 | `0x0000` | **明文可读写**（真正能用的数据槽） |

所以：
- 读 slot0 / slot5 → `0x0F`（执行错）是策略拒绝；
- `GenKey(Mode 0x04)` → `0x0F`，因为 slot0 的 `WriteConfig=2` 不允许造键；
- `Sign` 失败，因为 slot0 里本来就没有密钥。

**要真正用起来，必须：改配置区 → 写密钥/GenKey → 锁定（不可逆）。** 这三步的顺序不能颠倒。

## 五、顺带一个值得所有人注意的坑（我们自己的 bug）

读配置区时，**`SlotConfig[0]` 在偏移 `0x14`，不是 `0x20`**；`KeyConfig[0]` 在 `0x60`；
`RevNum` 在 `0x04–0x07`（不是 `0x08`）。我们一开始按 `0x20` 解读，把 `SlotConfig[6..15]`
当成了 slot0..9，于是得出了“Slot0 = 0x8F9F、WriteConfig=8(Never)”的错误结论，
并进一步误导了“器件是仿制件”的判断。

按正确偏移读这颗片：`2083 2087 208F 8FC4 8F8F 8F8F 8F9F 8FAF 0000×7 8FAF`，
其中 `0x8F9F` 是 **slot6**，不是 slot0。

## 六、给后来者的最短排查顺序

1. 用官方 `atCRC()` 校准 CRC（或直接抄上面那段），先让 `Info` 命令通；
2. 读配置区 `0x56/0x57`，确认是否锁定；
3. 未锁定 ⇒ `Random` 固定图案、数据区 `0x0F`、`GenKey` 失败**都是预期**，不要怀疑器件；
4. 想用密码学功能 ⇒ 规划配置区 → 写配置 → 锁定（**不可逆，务必先确认每一字节**）。
