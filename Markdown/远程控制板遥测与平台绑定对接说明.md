## 1. 角色与拓扑

```
DSO 过桥板 192.168.100.50
  ├─(TCP 客户端，7 帧/s)──▶ 遥测服务器 192.168.100.100:5005   [平台接收器]
  ├─(TCP 客户端，legacy)──▶ 同一 192.168.100.100:5005          [平台接收器]
  └─(TCP 服务端，单客户端)◀── 192.168.100.50:5005              [授权服务/控制工具]
```

- 遥测是**单向**的：板子主动连服务器，服务器不需要回包。
- 板子同时建立**两条**到 `.100:5005` 的 TCP 连接：
  1. `module.*` 信封（spec-00，模块遥测）；
  2. legacy v1.0 信封（`device.status` / `telemetry.io` / `telemetry.mode`）。
  接收器必须同时接受两条连接，并按**首行**分类。
- 控制通道是板子自己的 TCP 监听器（`.50:5005`，**单客户端**）：
  授权服务/平台主动连它，执行 `atecc.*`、`get_switch`、`set_sw` 等。
  遥测接收器是被动监听，不占用这个客户端位；但任何 GUI/其他控制客户端不能与
  `flow` 同时连。

## 2. 遥测通道

### 2.1 `module.*`（spec-00）

- 端点：设备→`192.168.100.100:5005`（固件编译期常量；换服务器需重编固件）。
- 帧：一行一个 JSON，CRLF 结尾；每秒 7 帧，顺序固定：
  `atecc608b, sht40, ina226_u10, ina226_u44, bgm_adc_dac, watchdog, pcal6524`。
- 信封：

```json
{"ver":"1.0","type":"module.data","module":"sht40","seq":123,"ts_ms":456789,"data":{...}}
```

- `seq`：该连接上全局自增，每帧 +1（约 7/s）；`ts_ms`：设备 FreeRTOS tick 毫秒，
  非墙上时钟；重启会归零（用 `seq`/`ts_ms` 回退识别 reboot）。
- `watchdog` 帧存在；本轮测试按需求**排除判定**，平台可以存储但不参与模块验收。
- 模块 data 字段与单位：

| 模块 | 字段（实际固件） | 单位/说明 |
|---|---|---|
| `atecc608b` | `present, comm_ok, device_id, chip_info{serial4, part, rev, lock_config, lock_data}, login_state, fail_cnt` | `device_id` 16 字符；`serial4` ≤8 hex；`rev` 是 **hex 字符串**；`login_state` 实际为 `NO_LICENSE` / `AUTHORIZED` |
| `sht40` | `temp_dezi, rh_centi, temp_ok, hi_alarm, level` | 温度 0.1℃；湿度 0.01%RH；`level` 0..3（58/60/65℃ 分级） |
| `ina226_u10` | `cur_ma, over_cur, valid, level` | 过桥板电流 mA；`valid` 固件恒 1；阈值 59.5/70/105mA |
| `ina226_u44` | `cur_ma, over_cur, valid, level` | 核心板电流 mA；`valid` 恒 1；阈值 136/160/240mA；**不发行事件** |
| `bgm_adc_dac` | `freq_valid, freq_state, freq_millihz, gate_us, edge_count, ref_ticks, overflow_count, last_edge_age_ms, overrange, sample_format, sample_rate, overrun_count` | 频率计快照；无外部信号时 `freq_valid=0`、`freq_state=4`（NO_SIGNAL） |
| `pcal6524` | `sw, yds, eth_link, usb_active` | `sw` 14 位（bit9=B10 恒 0）；`yds` 5 位；**`eth_link` 实际是 yds bit3（温度告警），不是网口链路**；`usb_active`=yds bit4 |

- 事件（`module.event`）：`atecc608b` 的 `tamper`、`sht40` 的 `sensor_lost`、
  `ina226_u10` 的 `overcurrent/recovered`；`ina226_u44` 暂无事件。
- 参考解码：`module_telemetry/python_ref/envelope.py` + `module_*.py`。
  **注意实际固件与 `packet_specs` 的差异**，解析前做归一化：

| 差异 | 规格/参考 codec | 实际固件 | 后端处理 |
|---|---|---|---|
| ATECC `login_state` | `LOGGED_OUT/CHALLENGE/LOGGED_IN` | `NO_LICENSE/AUTHORIZED` | 接受这两个值，或映射为 `LOGGED_OUT/LOGGED_IN` |
| ATECC `chip_info.rev` | int | 8 字符 hex 字符串 | 按字符串存/解析 |
| ATECC 额外字段 | 无 | 顶层 `device_id` | 忽略/存储 |
| `pcal6524.eth_link` | “netif up” | yds bit3（温度告警） | 需要真实链路时用控制通道 `get_switch.eth_link` |
| `ina226.valid` | 0/1 通信有效 | 恒 1 | 不能用来判断 I2C 失效；看 `cur_ma` 是否突降/为 0 |
| `ina226_u44` 事件 | 规格列出 | 固件不发送 | 不要等 U44 事件 |
| module 帧设备标识 | — | **无 `deviceId`** | 用 `atecc608b.device_id` / `get_devid.uid_hex` + 对端 IP |

### 2.2 legacy v1.0（第二条连接）

- 同端点 `.100:5005`，CRLF JSON 行；板子重启后重连。
- `device.status` 每 1s；`telemetry.io` / `telemetry.mode` 每 500ms。
- **不要用它的 `deviceId` 做身份**：固件里固定为 `"board-001"`，`bootId` 固定为 1。
- 它的价值：心跳/在线判定、`fmcReady`、`uptimeMs`（与模块 `ts_ms` 的时间基准校准）、
  FMC16 快照；平台可按 `type/messageType` 分派。

### 2.3 接收器要求

1. 监听 `0.0.0.0:5005`，**至少接受两条**来自同一板子的连接。
2. 按首行分类：
   - 含 `"ver":"1.0"` + `"module"` + `"type":"module.data|module.event"` → spec-00；
   - 含 `"protocolVersion"` / `"messageType"` → legacy v1.0。
3. 行缓冲、CRLF 分割；单行上限建议 ≥4 KB（固件行 ≤512 B，legacy ≤700 B）。
4. 记录原始行 + 接收墙钟 + 对端 IP；按 `module` 分派解码。
5. 完整性：`seq` 缺口、`ts_ms` 回退（reboot）、每条连接的重连次数。
6. 身份：module 帧无 `deviceId`；用 `atecc608b.data.device_id`（及 `uid_hex`）
   与对端 IP/MAC 绑定到平台设备。
7. 参考实现：`tools/rack_test/receiver.py`（双连接、分类、校验、RST 处理、JSONL）。

## 3. 设备身份、密钥与 License 现状

### 3.1 设备身份（机架实测）

| 项 | 值 | 来源 |
|---|---|---|
| `device_id` | `Eep21025E269FA2E`（10-30 的板）；**2026-11-03 .50 实测为 `Eep21025E2AE127A`** | `atecc608b.data.device_id` / `atecc.get_devid`；换板/换芯片会变，以实际值为准 |
| `serial4` | `01232916` | `chip_info.serial4`；**只是 UID 前 4 字节，不是唯一身份**（新旧板可相同），唯一键用 `device_id`/`uid_hex` |
| `part` / `rev` | `608B` / `00006003` | `chip_info.part/rev` |
| `lock_config` / `lock_data` | `0 / 0`（未锁定） | `chip_info` |
| `present` / `comm_ok` | `1 / 1` | 模块帧 |
| `uid_hex` | 96-bit UID 的 24 位 hex | `atecc.get_devid.uid_hex`（以真机返回为准） |
| `login_state` | `NO_LICENSE`（未绑定 License） | 模块帧 / `get_license` |

### 3.2 密钥模型（当前 DEV 构建）

| 密钥 | 位置 | 现状/用途 |
|---|---|---|
| 设备公钥 | `atecc.get_pubkey` 返回 128 hex | `DSO_AUTH_DEV_SOFTKEY=1` 时是**共享 DEV 软件公钥**（`dso_auth_soft.c`），不是每设备唯一、也不是片内密钥 |
| 设备私钥 | DEV 固件内的软件 P-256 测试私钥 | 公开测试材料，**不是生产密钥**；生产应使用 ATECC Slot0 片内私钥 |
| CA 公钥 | 设备固件 `User/dso/dso_auth_ca.h` | 用于验签 License；已与授权服务 `.state/ca_key.pem` 核对一致 |
| CA 私钥 | 授权服务 `.state/ca_key.pem` | **只留在授权服务**，不进平台库、不进设备、不进仓库 |
| License token | 授权服务签发，经 `atecc.auth_verify` 推给设备 | CA 签名；设备验签后写入 EEPROM；平台只存 `lic/jti/user/dev/nb/na/perm/revoked` 元数据 |

### 3.3 License 现状与命令

当前机架板 **未绑定 License**（`get_license` → `login_state=NO_LICENSE`, `license=null`）。
DEV 授权服务已具备完整链路（历史真机验证；本轮机架 run 只验证了命令，未跑 `flow`）：

| v0.9 命令 | 作用 | 关键返回 |
|---|---|---|
| `atecc.get_devid` | 读设备 ID/UID | `device_id,label8,uid_hex` |
| `atecc.get_pubkey` | 读设备公钥 | `pubkey_hex,slot,device_id`（softkey 为共享 DEV 公钥） |
| `atecc.auth_start {challenge_hex}` | 设备对 32 字节挑战签名 | `signature_hex,pubkey_hex,self_verify` |
| `atecc.auth_verify {token}` | 校验 CA License 并持久化 | `lic,user,dev,nb,na,perm` |
| `atecc.get_license` | 只读查询当前 License | `login_state,restored,license` |
| `atecc.license_clear` | 清除 EEPROM 中的 License | `cleared:1` |

- 设备无 RTC：`nb/na` 只上报，**时间有效性由服务器判定**；设备侧只验签/绑定。
- `restored=1` 表示重启后从 EEPROM 恢复；`login_state=AUTHORIZED` 表示当前持有有效 License。
- **复位后 `atecc608b.login_state` 可能暂时保持 `NO_LICENSE`**：软件后端从 EEPROM
  的恢复是惰性的，第一次 `atecc.get_license`（或 auth 命令）才触发。平台/授权服务
  应在设备上线后主动查一次 `get_license`，不要仅凭模块帧判断“无 License”。
- 生产强制授权前必须完成：ATECC Slot0 密钥预置 + Config/Data Lock，使
  `atecc.get_pubkey/auth_start` 走片内 ECDSA，且每设备唯一。

## 4. 平台绑定模型（建议）

### 4.1 实体与表

| 表 | 关键字段 | 说明 |
|---|---|---|
| `devices` | `device_id PK, uid_hex, serial4, pubkey_hex, capability, host, port, lock_config, lock_data, firmware, first_seen, last_seen` | `device_id` 为平台 join key；`uid_hex/serial4` 为不可变硬件身份；`pubkey_hex` 当前是 DEV 共享钥匙，仅 staging 使用 |
| `users` | `user_id PK, ...` | 平台账号；与授权服务账号可映射或共用 |
| `bindings` | `user_id, device_id, nb, na, revoked, created_at` | 用户↔设备租期；与授权服务 `bind` 一致 |
| `licenses` | `lic PK, jti, user_id, device_id, nb, na, perm, revoked, issued_at` | 只存元数据；**不存 CA 私钥/完整 token** |
| `telemetry_samples` | `device_id, module, ts_ms, received_at, data JSON` | 可按时间分区/时序库；原始 JSONL 兜底 |
| `events` | `device_id, module, event, level, ts_ms, detail` | `tamper/sensor_lost/overcurrent/...` |
| `audit` | 授权服务 `audit.jsonl` | 登录/授权/吊销/清除等操作审计 |

### 4.2 绑定原则

- **身份用 `device_id` + `uid_hex`**，不要用 `device.status.deviceId`
  （固定 `board-001`）或共享 DEV 公钥做唯一身份。
- **不要用 `serial4` 做唯一键**：它只是 UID 前 4 字节；实测新旧两块板
  `serial4` 都是 `01232916`，但 `device_id` 不同（`Eep21025E269FA2E` vs
  `Eep21025E2AE127A`）。平台主键必须是 `device_id`，`uid_hex` 作硬件指纹核对。
- 当前 `pubkey_hex` 是共享 DEV 公钥：可以登记用于 staging 验签，但**不能**把它
  当作“这台设备独有”的凭据。
- License 的签发/校验/吊销以**授权服务**为准；平台通过其 HTTP API 或 CLI 操作，
  不建议在平台内复制 CA 验签逻辑。
- 不存私钥：CA 私钥只在授权服务 `.state`；设备私钥应在 ATECC 片内（生产）。

### 4.3 授权服务接口（DEV）

- CLI（仓库根目录，`PYTHONPATH=.`）：
  `add-user` / `register` / `bind` / `flow` / `license` / `renew` / `revoke` /
  `negtest` / `probe` / `show-ca`。
- HTTP（默认 `127.0.0.1:8080`，DEV；见 `Markdown/设备授权协议_v0.md` §12）：
  - `POST /api/session`（user/password → sid）
  - `POST /api/authorize`（sid, device, ttl → 驱动设备 `auth_start`/`auth_verify`）
  - `GET  /api/device/{dev}/license`
  - `POST /api/admin/users`、`/api/admin/devices`、`/api/admin/bindings`
  - `POST /api/admin/revoke`、`GET /api/admin/licenses`、`GET /api/admin/audit`
  - `POST /api/admin/device/{dev}/clear-license`
- 安全：默认只监听回环；开放 LAN 需 TLS/白名单；`.state/ca_key.pem` 是命根子，
  备份加密、权限 600，禁止提交。

### 4.4 授权时序

```
平台/管理员 -> 授权服务: add-user / register(device_id, pubkey, host, port) / bind
用户/平台   -> 授权服务: /api/authorize (sid, device)
授权服务    -> 设备 .50:5005: atecc.get_devid / get_pubkey
授权服务    -> 设备: atecc.auth_start(challenge)
设备        -> 授权服务: signature_hex (DEV 模式为软件 P-256)
授权服务: 验签 -> 签发 CA License token
授权服务    -> 设备: atecc.auth_verify(token)
设备: 验 CA 签名 -> 写 EEPROM -> login_state=AUTHORIZED
平台: 记录 binding/license/jti/audit；订阅 atecc608b 帧的 login_state
```

## 5. 平台接入步骤

1. **部署接收器**：在 `192.168.100.100:5005` 监听，接受两条连接；按 §2.3 解码。
   - 设备侧服务器 IP 是编译期常量；若平台不在 `.100`，必须改固件重烧。
2. **部署授权服务**：放在能主动连 `192.168.100.50:5005` 的机器（机架服务器最合适）；
   复制 `tools/auth_server` 与**匹配的 `.state`**（CA 私钥/台账），安装 `cryptography`。
3. **登记设备**：`register Eep21025E269FA2E <128-hex DEV 公钥> --host 192.168.100.50 --port 5005`；
   公钥以 `atecc.get_pubkey` 实际返回为准。
4. **建用户/绑定**：`add-user <user>` + `bind <user> Eep21025E269FA2E --days 30`。
5. **授权**：`flow --host 192.168.100.50 --port 5005 --user <user>`（或 `/api/authorize`）。
6. **验证**：`license --host ...` 看 `login_state=AUTHORIZED`、`lic/user/nb/na/perm`；
   重启后再查 `restored=1`（可选）。
7. **关联遥测**：`atecc608b.data.device_id`/`login_state` 与平台 `devices/licenses` 对账；
   `tamper/sensor_lost/overcurrent` 入事件表；`level` 驱动告警。
8. **运维**：续期 `renew`、吊销 `revoke --jti/--device`、清除 `license_clear`、
   审计导出；设备离线以 `device.status` 3s 心跳判定。

```bash
#      'tar xzf - -C ~/dso_rack_test'

rm -f ~/dso_rack_test/tools/auth_server/.state/server.lock

# 2) 取当前设备实际 ID/公钥（换板后必须用新 ID），登记 + 建用户 + 绑定
cd ~/dso_rack_test
DEVICE=$(PYTHONPATH=$PWD python3 -m tools.rack_test cmd --config config.json get_devid \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["device_id"])')
PUB=$(PYTHONPATH=$PWD python3 -m tools.rack_test cmd --config config.json get_pubkey \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"]["pubkey_hex"])')
echo "DEVICE=$DEVICE"
PYTHONPATH=$PWD python3 -m tools.auth_server.service register \
  "$DEVICE" "$PUB" --host 192.168.100.50 --port 5005

PYTHONPATH=$PWD python3 -m tools.auth_server.service add-user racktest --password '<测试口令>'
PYTHONPATH=$PWD python3 -m tools.auth_server.service bind racktest "$DEVICE" --days 30 --force

# 3) 完整 flow（会打开板子 5005 单客户端；不要同时跑 GUI/run 控制）
#    若 connect timed out：先确认 timeout 3 bash -c '</dev/tcp/192.168.100.50/5005'
#    可连；单客户端可能被旧连接卡住，复位板子后重试。
#    若 flow 报 bad credentials：add-user 是覆盖式，重设测试口令（见第 2 步）。
PYTHONPATH=$PWD python3 -m tools.auth_server.service flow \
  --host 192.168.100.50 --port 5005 --user racktest
# 期望：device proof: OK / verify: OK  lic=... user=racktest ...
# 不要外传 flow 输出里的 license 前缀

# 4) 查询设备当前 License
PYTHONPATH=$PWD python3 -m tools.auth_server.service license \
  --host 192.168.100.50 --port 5005
# 期望：login_state=AUTHORIZED, lic/user/nb/na/perm, restored=no
# 可选：复位板子后再查，restored=yes（EEPROM 持久化）
```

## 7. 生产前必须补齐

1. **ATECC 片内密钥与 Lock**：Slot0 生成/写入 ECC 私钥，Config/Data Lock；
   `get_pubkey/auth_start` 走片内 ECDSA，每设备唯一；关闭
   `DSO_AUTH_DEV_SOFTKEY`。
2. **传输安全**：遥测/控制加 TLS 或 mTLS；控制通道加客户端认证；
   遥测帧如需防篡改，增加签名/HMAC（当前明文、无认证）。
3. **授权服务生产化**：TLS、systemd、CA 备份/轮换、审计归档、Host/Origin
   白名单；不要把 DEV `.state` 当生产根。
4. **平台接收器生产化**：双连接、断线重连、seq/ts 校验、坏帧告警、原始日志
   保留策略、时序库/告警去重。
5. **时间与租约**：设备无 RTC；License 的 `nb/na` 由服务器判定；平台需处理
   续期/吊销/离线。
6. **字段/规格对齐**：把 `packet_specs/01` 与 `module_telemetry/python_ref`
   按实际 `NO_LICENSE/AUTHORIZED`、`rev` 字符串、额外 `device_id` 修正，避免
   后端用参考 codec 误判坏帧。
