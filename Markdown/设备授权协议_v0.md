# 设备授权协议 v0（DEV，2026-10-21）

> 依据 `Markdown/STM32H743 + ATECC608B-SSHDA-T + LCMXO2 FPGA 远程学生设备授权体系.md`，
> 在**当前器件状态**（ATECC 配置区未锁定、无可用密钥）下的可执行版本。
> 实现：`tools/auth_server/`（PC 侧服务） + `dsosim/atecc.py`（模拟已预置设备）。

---

## 0. 一句话

服务器负责**策略与审计**：谁、在哪台设备、什么时候、能做什么；
设备侧最终要用一颗**已预置并锁定**的 ATECC 来证明身份和校验 License。
**当前这颗片子两件事都做不到**，所以本版本先把协议与 PC 侧闭环做出来。

---

## 1. 角色与通道

| 角色 | 位置 | 现状 |
|---|---|---|
| 授权服务（本文主角） | PC | 已实现（`tools/auth_server`） |
| 学生客户端 | PC/网页 | 未实现（CLI 代替） |
| 设备 | STM32H743 | 已实现 `atecc.get_devid`；`get_pubkey`/`auth_start` 在未锁定器件上回 `rc=-4 st=0x0F` |
| 模拟设备 | `dsosim` | 已实现 `atecc.*`（软件密钥，可切 `provisioned=False` 模仿真机） |

**通道**：设备是 TCP 服务端（5005），单行 JSON v0.9：

```
请求  {"cmd":"...","params":{...},"seq":N}
应答  {"ver":"0.9","type":"ack","seq":N,"cmd":"...","result":"ok|error","error":"...","data":{...}}
```

- `seq` 由请求方给、设备**原样回显**；
- 同一连接上会混有周期遥测帧，客户端按 `type=="ack"` 过滤；
- **单客户端**：长连接会挡住 PC 面板，服务端每次流程用完即断；
- 命令行缓冲 **512 字节**，超长会被静默截断 ⇒ 客户端本地拒绝 >480 字节的请求。

## 2. 设备证明（challenge / response）

设备只会对一个 **32 字节挑战**签名（`Nonce(0x16, Mode 0x03)` → 挑战直接成为摘要 →
`Sign(0x41, Mode 0x80)`），固件既不知道 DeviceID 也不带时间戳。因此由**服务器**构造有语义的挑战：

```
challenge = SHA256( "DSO-PROOF-V1" || device_id(ASCII) || nonce(32B) || ts_be64 )
```

- 服务器保存 `challenge` 作为一次性票据；
- 设备把 `challenge` 当**摘要**直接签名（固件语义如此，PC 侧验签必须用 `Prehashed(SHA256)`，
  **不能再哈希一次**）；
- 这样即使有人滥用 5005 上的签名接口，签出的也只是"带设备 ID 与时间戳的摘要"，
  不能当别的用途的签名。

**应答**：`signature_hex`（r‖s 64 字节）、`pubkey_hex`（X‖Y 64 字节）、`self_verify`（片内验签结果）。

**判定**：

| 条件 | 处理 |
|---|---|
| 用**台账登记**的公钥验签通过 | 证明成立 |
| 响应里的 `pubkey_hex` 与台账不一致 | 拒（防止换钥） |
| `self_verify != 1` | 拒 |
| 同一挑战第二次提交 | 拒（提交即消费） |
| 挑战超 120 s | 拒 |
| 挑战跨会话/跨设备使用 | 拒 |

> ⚠️ ATECC 的 `Sign` 约有**一半概率输出 high-s**（`s > n/2`）。验**设备证明**时
> 必须接受 high-s（内部归一化为 `n-s` 再验）；验 **License** 时要求 low-s
> （我方签发时已归一化，一种 License 只有一种编码）。

## 3. License token 格式 v0

```
token  = b64url(payload_bytes) "." b64url(sig64)
sig64  = ECDSA-P256(CA) over SHA256(payload_bytes)        # low-s，r‖s
```

**payload**：单层 ASCII JSON，键按字节序排序、无空白、无转义、**只允许整数**、不允许布尔/浮点/null/嵌套。

```json
{"dev":"Eep21025E269FA2E","jti":"9b5c87baf03c7f99","kid":"k1","lic":"L00001",
 "na":1749000900,"nb":1749000000,"perm":1,"typ":"lic","user":"stu001","v":1}
```

| 字段 | 类型/长度 | 约束 |
|---|---|---|
| `v` | int | 必须 `1` |
| `typ` | str | 必须 `"lic"`（域分隔，防跨用途复用） |
| `lic` | str ≤16 | License 编号 |
| `user` | str ≤32 | 学生账号 |
| `dev` | str =16 | 必须等于设备自身 DeviceID |
| `nb`/`na` | uint32 | **自 2020-01-01 起的秒数**（到 2156 年，避开 2038 与固件 32 位写法） |
| `perm` | uint32 | bit0 = FPGA 操作权；**未知位一律拒绝**；`perm=0` = 只读 |
| `jti` | str ≤16 | 64-bit 随机 + 台账唯一性检查（吊销/去重的键） |
| `kid` | str ≤4 | CA 密钥编号（审计/轮换；锁定的 ATECC 只有一个 CA 槽） |

**长度预算**：payload ≤192 B、token ≤340 B、整条请求 ≤480 B（固件 512 B 缓冲）。

**解析规则（严格）**：非 ASCII、重复键、浮点、未知键、未知 `v`、未知权限位、`na < nb`、
非规范 base64url（含 `=`、`+`、`/`、非零尾位）、长度超限 —— 全部拒绝。

**为什么"对原始字节验签"**：CA 签的是序列化后的 payload 字节；验方对**收到的字节**做 SHA-256
再验，`parse_payload` 额外要求"重新序列化后与输入逐字节相同"（拒绝空白/键序/转义差异）。
这样不存在"验签用一套规范化、签发用另一套"的漂移。

## 4. 流程

```
登录            服务端校验口令（PBKDF2-HMAC-SHA256, 600k 迭代 + 每用户盐）
  │
下发挑战 ────────→ device: atecc.auth_start(challenge_hex)
  │                        │ 设备签名（片内，私钥不出片）
  │ ←──── signature_hex ───┘
验签（台账公钥, Prehashed, 允许 high-s）
  │
检查绑定（user ↔ device 在有效期内）＋能力（identity_only 不得拿 FPGA 权限）
  │
签发 License ─────→ device: atecc.auth_verify(token)
                             │ 设备解析 payload，对原始字节做 SHA-256，
                             │ Nonce(Mode 0x03) → Verify(Stored, CA 槽)
  │ ←──── ok / error ───────┘
设备按 perm 开放 FPGA 通道
```

**只有登录不签发**：同一会话里必须**既有完成的设备证明、又有有效绑定**。

## 5. 能力协商（当前器件的关键）

`atecc.auth_start` 的错误串带 `rc=` 与 `st=0xNN`：

| 判据 | 能力 | 处理 |
|---|---|---|
| 成功 | `provisioned` | 可签发含 FPGA 权限的 License |
| 连续 3 次里 ≥2 次 `st=0x0F` | `identity_only` | **不签发任何 License**（见下） |
| 只有 `st=0xEE` / `rc=-1` | 瞬态，**不降级** | 重试 |
| `get_devid` 就失败 | `no-identity` | 拒绝一切 |

**`identity_only` 为什么连只读 License 也拿不到**：签发的前提是"同一会话里完成了设备证明"，
而这类设备恰恰**证明不了自己**。没有证明就签发，等于把授权发给一个只报了串号的陌生对端
（DeviceID 是固件常量 + UID 的 CRC32，可仿造）。因此实现上是"证明 ⇒ 才可能签发"，
`perm` 里的 FPGA 位另有独立检查（用于"曾预置、后来被降级"这种情形）。

### 5.1 provisioned 与 identity_only 的区别

| | `provisioned` | `identity_only` |
|---|---|---|
| `atecc.get_devid` | ✔ 可读 | ✔ 可读 |
| `atecc.auth_start`（设备证明） | ✔ 能对挑战签名 | ✘ 回 `rc=-4 st=0x0F` |
| 服务器能否确认"这就是那台真设备" | ✔ 用台账公钥验签 | ✘ 只看到一个可伪造的 DeviceID |
| 能否签发 License | ✔ | **✘ 一张都不发** |
| FPGA 权限（`perm=1`） | 可以 | 不适用（拿不到 License） |
| 典型成因 | 已预置并锁定的 ATECC；或 Stage 2C 软件后端 | ATECC 出厂**未锁定**、Slot0 无密钥（当前板子） |

一句话：**`provisioned` 是"能证明自己"，`identity_only` 是"只能报个名字"。**
名字（DeviceID）是固件宏 + UID 的 CRC32，任何人在局域网里都能照抄；只有对服务器随机挑战的
签名才证明"私钥在这台设备里"。所以 `identity_only` 的设备在协议里是**只读可见、不可授权**的——
不是被处罚，而是它确实没有可被验证的身份。

当前这块板子就是 `identity_only`（ATECC 未锁定）；启用 `DSO_AUTH_DEV_SOFTKEY`（Stage 2C）
后软件后端能签名，能力判定随之变成 `provisioned`。

> 若业务上确实要给未预置设备发只读授权，必须先补一个**带外的信任前提**
> （例如管理员按物理标签核验后手工绑定），这是策略决策，不属于当前实现。

**真机实测（2026-10-21，192.168.100.50）**：

```
device_id:   Eep21025E269FA2E
pubkey_hex:  None
capability:  identity_only
  note: get_pubkey: pubkey read failed rc=-4 st=0x0F (Slot0 has no ECC key?)
  note: auth_start: sign/verify failed rc=-4 st=0x0F (...) -> no-key   ×3
```

与 `Markdown/ATECC608B_结论_配置区未锁定.md` 的判断一致；错误串的实际措辞与模拟器不同，
但分类器只看 `st=0x0F`，因此不受文案影响。

## 6. 新鲜度、时间、吊销

| 项 | 规则 |
|---|---|
| 挑战 | 32 B 随机；TTL 120 s；**提交即消费**；每设备最多 4 个未用 |
| License 有效期 | 默认 15 min，服务器判定；心跳/重连时重签 |
| 吊销 | 台账按 `jti` 标记；离线设备**收不到**吊销（见下） |
| 设备时钟 | **没有**（RTC 未启用、无 SNTP）⇒ `nb/na` 在设备侧**只作参考**，时间判定只能在服务器 |

## 7. 安全边界（必须写在最显眼的位置）

**本版本保护的是**：口令不外泄、签发有据可查、挑战不可重放、跨用户/跨设备不可挪用。

**本版本不保护**：

1. **设备真实性** —— `atecc.get_devid` 完全不碰芯片：它是固件宏 `DSO_DEVICE_LABEL` 的
   前 8 字符 + `CRC32(STM32 UID)`，可预测、可仿造；
2. **链路** —— 明文 TCP，无 TLS、无对端认证；同网段任何人都能冒充设备、调用签名接口、
   抓走 License；
3. **设备侧执行** —— 未锁定的 ATECC 不能验签，License 在设备上**无法被强制**；
4. **吊销时效** —— 离线设备永远不知道 License 被吊销（bearer token）；
5. **固件** —— 改过的固件可以完全无视本协议。

⇒ 结论：**今天它是"策略 + 审计 + 集成骨架"，不是设备可信证明，也不是设备侧强制授权。**

## 8. 与架构文档的差异（不可直接落地的 10 点）

| # | 架构文档说法 | 现状/更正 |
|---|---|---|
| 1 | Slot2 = CA 公钥 | Slot2 是出厂 ECC 私钥槽（`0x208F`，36 B 且不可写）；P-256 公钥需 72 B ⇒ 只能用 **slot 8–15** |
| 2 | Slot3 = License | token ~300 B，**任何槽都放不下**（最大 72 B）⇒ RAM 解析，持久状态另存 |
| 3 | Slot1 = DeviceID | Slot1 是 ECC 私钥槽（`WriteConfig=2` 不可写）；当前 DeviceID 是软件派生 |
| 4 | ATECC 校验 License 时效 | ATECC 不是时钟也不是 JSON 解析器 ⇒ 时间判定只能在服务器 |
| 5 | 设备对 "Nonce+DeviceID+时间戳" 签名 | 固件只签 32 字节 ⇒ 由服务器构造含 DeviceID/时间戳的**摘要**（§2） |
| 6 | TLS 1.3 + AES-GCM | 工程内无 TLS 栈；本版本明文 |
| 7 | 随机段用硬件随机源 | 当前是 UID 的 CRC32（可预测）；升级需写 Slot1 ⇒ 属 Stage 2B |
| 8 | 服务器存口令 SHA256 加盐 | 改为 **PBKDF2-HMAC-SHA256 600k**（裸 SHA-256 太快） |
| 9 | HSM 保管 CA | 本版本是本机 PEM（`.state/`，已 gitignore） |
| 10 | "私钥不出片、设备不可克隆" | **锁定并预置之后才成立**；未锁定前一句都不成立 |

另：架构文档把设备当 TCP **客户端**连服务器，而现行 v0.9 通道是设备当**服务端**。
本协议沿用 v0.9（与 Stage 1 一致），后续若切 v1.0 需要另立迁移方案。

## 10. Stage 2C：设备侧软件 P-256（DEV）

ATECC 未锁定 ⇒ 数据区不可用 ⇒ 设备证明与 License 验签都做不了。2C 用**软件**实现这两件事，
**完全不接触 ATECC**（不发任何写命令、不 Lock、不碰 OTP）。

| 项 | 实现 |
|---|---|
| 加密库 | **mbedTLS 2.28.3**（`Middlewares/Third_Party/mbedtls/`，裁剪：P-256 + ECDSA + SHA-256，无 ASM/无熵源） |
| 内存 | **4 KB 固定 arena**（`MBEDTLS_MEMORY_BUFFER_ALLOC_C`），不占 FreeRTOS 堆；`ECP_WINDOW_SIZE=2` |
| 设备私钥 | 公开测试密钥 `00 01 … 1F`（`dso_devkey.c`，与 ATECC 预置路径共用同一份定义） |
| 签名 | `mbedtls_ecdsa_sign_det_ext()`（RFC6979，**无需 RNG**），输出裸 `r‖s` |
| 验签 | 接受 **high-s**（ATECC 也会输出 high-s；mbedTLS 只校验 `1≤r,s<n`） |
| License 解析 | 设备侧严格版：base64url（规范）+ 固定键序的规范 JSON + 字段校验 + `dev` 绑定 + CA 验签 |
| CA 公钥 | 编译期常量 `User/dso/dso_auth_ca.h`，由 `python -m tools.auth_server.service show-ca --c` 生成 |
| 开关 | `DSO_AUTH_DEV_SOFTKEY`（`dso_config.h`，本轮 `1`）；开机打印 `*** DEV SOFTWARE KEY ENABLED ***` |
| 生效范围 | `atecc.get_pubkey` / `atecc.auth_start` / `atecc.auth_verify` |
| **不做的** | **不拦截** `set_sw`/FPGA（只把 `login_state` 上报为 `AUTHORIZED`）；**不校验时间**（设备无时钟） |

**通道限制**：ECDSA 约 3.5 KB 栈，只有 TCP 通道（`ETH_Up` 任务，10 KB 栈）能跑；
串口通道（`SW_Ser`，2 KB）上的 `atecc.auth_*` 会直接回
`"use the TCP channel for auth (serial task stack is too small)"`。

**它不是什么**：私钥在 Flash 里、可被复制，**不提供防克隆**；验证的是协议与产品流程，
不是硬件安全。切回 2B（预置并锁定 ATECC）时，替换的是同一个后端接口。

### 10.1 真机实测（2026-10-21，192.168.100.50）

```
$ python -m tools.auth_server.service flow --host 192.168.100.50 --user stu001
device_id   : Eep21025E269FA2E
challenge   : e40e665897b46b1777661f7e73024d2e...
signature   : 4F52B1810C111425ABCD7364F8BB93F2 ...
device proof: OK
license     : eyJkZXYiOiJFZXAyMTAyNUUyNjlGQTJFIiwianRp ... (287 bytes)
verify      : OK  lic=L00001 user=stu001 na=214736888 perm=1
=> full authorization chain works on this device
```

链路四段全部在真机上成立：挑战构造（PC）→ **ECDSA 签名（STM32）** → 服务器验签 →
License 签发（PC）→ **License 验签（STM32）**。ATECC 未参与，也未做任何写入。

### 10.2 真机负向验证（2026-10-21，`service negtest`）

只验证"好的能通过"说明不了任何事——必须证明"坏的会被拒"。在真机上逐条打穿：

```
case                             res  detail
baseline good license            PASS L00002
payload byte flipped             PASS code=-2 (malformed token)
license for another device       PASS code=-3 (token bound to another device)
signed by another CA             PASS code=-4 (signature invalid)
signature bit flipped            PASS code=-4 (signature invalid)
unknown permission bit           PASS code=-2 (malformed token)
malformed token (no separator)   PASS code=-2 (malformed token)
7/7 PASS
```

覆盖了 `atecc.auth_verify` 的全部三条拒绝分支（`-2` 格式 / `-3` 设备绑定 / `-4` 签名），
并额外验证了 `perm` 的未知位掩码——即"设备侧确实在检查，而不是一律放行"。

### 10.3 资源实测（2026-10-22，ETH_Up 任务）

```
[AUTH-SW] after selftest: stack_free=1505 words, heap_free=47184 B (min 46968 B),
                          arena_max=2204 B/44 blk, arena_cur=320 B
[AUTH-SW] after sign:     同上
```

| 指标 | 实测 | 判读 |
|---|---|---|
| 栈余量（ETH_Up，共 2560 words） | **1505 words ≈ 6.0 KB** | 峰值约 4.2 KB，余量充足 |
| 堆余量 | **47,184 B**（历史最低 46,968 B） | 远未耗尽 |
| arena 峰值 | **2,204 B / 4,096 B** | 余量 1.8 KB；`ECP_WINDOW_SIZE=2` 合适 |
| arena 稳态 | 320 B | 只有 ECDSA 期间才增长 |

**实测耗时（-O1、`ECP_WINDOW_SIZE=2`、无汇编）**：

| 操作 | 耗时 |
|---|---|
| 惰性初始化（组加载 + 自检：1 验签 + 1 签名 + 1 验签） | **2,903 ms**（一次性）|
| 签名（RFC6979） | 462–464 ms |
| 验签 | 1,118–1,320 ms |

⇒ 首次 `atecc.auth_start` 约 3.4 s（含初始化），之后每次签名 ~0.46 s、每次验签 ~1.1 s。
PC 客户端的 ACK 超时因此放宽到 **20 s**（连接仍限 5 s）。若日后需要更快，可把 mbedTLS
单独开到 `-O2`，或把 `ECP_WINDOW_SIZE` 提到 4–5（arena 需同步加到 8 KB）。

> **初始化必须是惰性的**：`DSO_AuthSoft_Init()` 早期版本在 `main()` 里做 mbedTLS
> 初始化 + 自检，跑在 **4 KB 的启动栈**上且调度器尚未启动 ⇒ 上电即挂（无串口输出、
> 外设不动）。现已改为首次签名/验签时在 ETH_Up 任务里执行（提交 `50d782d`）。
> 同时去掉了多余的 8 KB 初始化任务。

### 10.4 授权状态可见（A）

设备侧记住最近一次**验签成功**的 License，并提供只读查询：

```
-> {"cmd":"atecc.get_license","params":{},"seq":N}
```

## 11. 续期与吊销（B，2026-10-22）

| 动作 | 命令 | 效果 |
|---|---|---|
| 续期 | `service renew --host <IP> --user <u>` | 设备证明 → 服务器签发**新** License（新 `jti`）→ 推给设备 `auth_verify` → 设备缓存替换 |
| 吊销单张 | `service revoke --jti <id>` | 该 License 立刻无法通过服务器校验 |
| 吊销整机 | `service revoke --device <id>` | 撤销该设备**全部**绑定与已签发 License；此后**不再签发** |
| 查询 | `service license --host <IP>` | 读设备当前缓存（可能尚未更新） |

**设备侧的实际行为（2026-10-22，真机 192.168.100.50）**：

```
revoke --device Eep21025E269FA2E      -> 4 record(s) marked
renew  --host … --user stu001         -> 拒绝：no active user<->device binding
license --host …                      -> NO_LICENSE（该轮之前重新烧录过，RAM 缓存已清空）
bind   stu001 Eep21025E269FA2E        -> binding added
renew  --host … --user stu001         -> renewed lic=L00004
license --host …                      -> AUTHORIZED / L00004 / na=214802147
```

> ⚠️ License 缓存**在 RAM 里，重启即失**（License 是会话凭证，不是持久配置）。
> 所以"吊销后设备仍持有旧证"只在该设备**未重启**时成立；一旦重启，`license` 就是
> `NO_LICENSE`。要跨重启保留，必须写入 Flash 或（将来）ATECC Slot3，二者都不在本阶段。

**能力边界（必须理解）**：

1. 设备**没有时钟**、也**没有推送通道** ⇒ 吊销在设备侧**不会立刻生效**；
2. 真正的执行力在**服务器**：吊销后不再续签，设备手里的旧 License 一到期就再也换不到新的；
3. 设备缓存只在下一次 `auth_verify` 成功时被替换（`renew` 正是利用这一点）；
4. 若要"立刻断权"，需要设备在线且服务器主动下发 —— 当前 5005 是**设备作服务端、单客户端**，
   推送要另设通道，属后续工作。

> 因此 `revoke` 的语义是"**不再授权它继续用**"，而不是"立刻让它停机"。
> 这一点与 §7 的安全边界一致：设备侧强制能力取决于将来是否用锁定后的 ATECC 来做。

## 12. HTTP/JSON API（2026-10-22）

```bash
python -m tools.auth_server.http_api --port 8080        # 只监听 127.0.0.1
```

- **明文 HTTP**：默认只绑回环；绑定其它地址必须显式 `--unsafe-lan`（文档即警告）。
- **admin token**：首次启动生成到 `.state/admin_token`（0600），经 `X-Admin-Token` 头传入，
  恒定时间比较，失败 10 次/分钟限流。绝不放在 URL 里。
- **单进程**：启动时在 `.state/server.lock` 上独占；已有实例则拒绝启动。
- **设备地址**来自登记记录（`host`/`port`），**绝不**从请求体取 —— 否则 API 就成了内网扫描器。

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/health` | 无 | 存活探针，不取任何锁 |
| POST | `/api/session` | 无 | `{user,password}` → `{sid,user,expires_at}`；会话 30 min |
| POST | `/api/session/logout` | sid | 注销 |
| POST | `/api/authorize` | sid | `{sid,device,ttl?}` → 服务端完成挑战/证明/签发/推送 |
| GET | `/api/device/<id>/license` | sid 或 admin | 设备当前缓存 |
| GET | `/api/admin/devices` | admin | 台账（含 host/port、绑定数） |
| GET | `/api/admin/audit?limit=&event=&device=` | admin | 最近 N 条审计（≤500），可按事件/设备过滤 |
| GET | `/api/admin/audit/export?event=&device=` | admin | 导出 CSV（最多 500 条） |
| POST | `/api/admin/users` | admin | `{user,password}`（≥8 字符） |
| POST | `/api/admin/devices` | admin | `{device,pubkey,host,port,capability}` |
| POST | `/api/admin/bindings` | admin | `{user,device,days}` |
| POST | `/api/admin/revoke` | admin | `{jti}` 或 `{device}` |

**并发模型**：每台设备一把锁（同一设备的授权串行化，拿不到 1 s → `409 device_busy`），
服务/台账调用用一把**短**全局锁包住，**绝不**在设备往返期间持有全局锁 ——
否则一台设备的 3 s 初始化会拖住所有请求（已用"慢设备时 health 仍 <200 ms"的用例守住）。

**与 CLI 共存**：服务长期运行、台账在内存里，但管理员可能用 CLI 改设备登记。因此每个请求
（`/api/health` 除外）处理前都会按文件 mtime 重新加载 `store.json`，CLI 的改动**立即可见、
无需重启**。仍应避免同一瞬间两边同时写（台账是整文件重写模型）。

**请求防护**：必须 `Content-Length`（411）；拒绝 `Transfer-Encoding`/`Content-Encoding`（400）；
体积上限 8 KiB（413）；只接受 `application/json`（415）；严格 UTF-8、顶层必须是对象、
拒绝重复键与浮点；`Host` 必须是回环（421）；带 `Origin` 的请求一律拒绝（403）。

**状态码**：400 参数/JSON、401 凭据/会话/admin、403 无绑定/能力/证明、404 未知路由/设备/jti、
405 方法（带 `Allow`）、409 挑战已用/设备不匹配/重复/忙、410 已吊销/过期、413 过大、
429 限流、502 设备协议错、503 忙/store 失败、504 设备超时（**结果未知，先查询再重试**）、500 内部。

**推送失败即吊销**：设备拒收刚签发的 License 时，服务器立刻吊销该 `jti`
（否则会留下一张"设备根本没有"的有效证），并审计 `license_push_failed`。

### 12.1 审计 `.state/audit.jsonl`

每行一个 JSON：`{"ts":<秒>,"event":"...","user":...,"device":...,"lic":...,"jti":...,"peer":...,"detail":...}`

记录：服务启停、登录成功/失败/锁定、会话创建/注销、授权各阶段结果、签发（lic/user/dev/jti/na/perm）、
推送与自动吊销、设备查询、全部 admin 变更、所有被拒请求（含状态码）、设备超时/传输错、内部错误。

**绝不记录**：密码、PBKDF2 盐/哈希、admin token、CA 私钥、License token 原文、原始请求体、
认证头；会话只记 `sha256(sid)[:8]` 用于关联。审计用独立文件与锁，写失败只打 stderr，不影响请求。

### 12.2 真机验证（2026-10-22）

```
POST /api/authorize  -> 200
  ok=True lic=L00005 user=stu001 dev=Eep21025E269FA2E na=214810731 perm=1
  device_ack={lic=L00005, user=stu001, dev=..., nb=..., na=..., perm=1}

GET /api/device/Eep21025E269FA2E/license -> 200
  login_state=AUTHORIZED  license={lic=L00005, ...}
```

服务在 `127.0.0.1:8080`、设备在 `192.168.100.50:5005`，中间由服务端自行驱动（学生端不直接碰设备）。

> 排障记录：服务启动后用 CLI 重新登记设备地址，`/api/authorize` 仍报 `device_no_address` ——
> 原因是服务把台账读进内存后不再读盘。已改为每个请求前按 mtime 重新加载（提交 `cc21740`），
> CLI 改动对运行中的服务立即可见。

## 13. Web 界面（2026-10-22）

`http_api` 启动后直接打开：

| 地址 | 角色 | 能做什么 |
|---|---|---|
| `http://127.0.0.1:8080/` | 学生端 | 登录 → 选设备 → **授权 / 续期** → 查看设备当前 License → 登出 |
| `http://127.0.0.1:8080/admin` | 管理端 | 令牌 → 设备台账（含命令地址/绑定数）、建用户、登记设备、绑定、吊销、审计（10 s 自动刷新） |

实现：`tools/auth_server/web/`（**纯静态**：HTML + CSS + 少量原生 JS，无框架、无 CDN、无构建步骤）。

安全要点：

- 脚本全部**外置**，页面无内联 `<script>` 与 `onclick`，服务器下发
  `Content-Security-Policy: default-src 'self'; script-src 'self'; ...`；
- 所有请求走同源相对路径；服务器只接受与自身同端口的 `Origin`，其它一律 `403 cross_origin`
  （浏览器同源 POST 也会带 `Origin`，这是必须放宽的原因）；
- `sid` 与 admin token 存 **sessionStorage**（关标签页即失），不落 cookie、不进 URL；
- 静态路由只允许 `web/` 下的**单段文件名**；`..`、`%2e`、前导 `.` 一律拒绝，状态文件与 `.py` 不可达；
- 学生端的 `/api/devices` 只返回 `device + capability`，**不含** pubkey / host / port。

验证：`http_test.py` 覆盖静态页与资源、路径穿越、同源/跨源 Origin、`/api/devices` 鉴权与字段收敛；
浏览器手工验收见 §12.2 的真机流程。
